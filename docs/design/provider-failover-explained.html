Provider Failover, Explained

A companion to the technical design spec — written for an engineer who knows infrastructure cold but not the Python SDK internals. If you've configured a load balancer or a circuit breaker in a service mesh, you already understand most of this.

ForPlatform / DevOps engineers Reads in~10 min Jargondefined as we go Pairs withthe technical spec

Here's the whole feature in one sentence: when the AI provider your app depends on goes down or starts rate-limiting you, the app automatically reroutes to a different AI provider and keeps working — decided locally, in milliseconds, with no extra server to run.

That's it. The rest of this doc unpacks why that simple idea takes a careful design — and it does so using analogies from the world you already live in: load balancers, health checks, retries, and timeouts.

Your mental model

This is failover for AI providers — the same pattern HAProxy or Envoy gives you for web backends, but moved inside the application library instead of living in a proxy or sidecar. The provider (OpenAI, Anthropic, Google) is the "backend." A circuit breaker tracks each one's health. When the primary is unhealthy, traffic shifts to the next backend in an ordered list.

Section 01

The problem in 60 seconds

Solwyn is a thin library your app wraps around an AI provider's client. Today, if you build on OpenAI and OpenAI has a bad hour, your AI features fail. The library can currently only retry with a different OpenAI model — which is useless when the problem is OpenAI itself (an outage, a regional issue, or your account hitting a rate limit).

● Today

One provider, one point of failure

App → OpenAI. If OpenAI is down, the only "fallback" is another OpenAI model — same company, same outage. Your agent goes down with the provider.

● The goal

An ordered chain across companies

App → OpenAI, and if that's unhealthy → Anthropic → Google. A different company entirely. Your agent stays up while one vendor has a bad day.

Like you already do

A web load balancer with two backend pools: when the primary pool fails health checks, traffic drains to the secondary. We want exactly that reliability posture — but the "backends" are rival AI companies, and (as the next section shows) that one difference is where all the engineering goes.

Section 02

Why it's harder than normal failover

When a load balancer fails over between web servers, it's easy because every backend is an identical clone. The same HTTP request works on any of them. Rerouting is just "send the same bytes somewhere else."

AI providers break that assumption. Each one speaks a different dialect — the request has to be shaped differently, and the response comes back shaped differently too. You can't just resend the same bytes. You have to translate.

OpenAI

One grammar

Wants a list of messages, with the system instruction as one of those messages. Max length is optional.

Anthropic

A different grammar

Also messages, but the system instruction is a separate field — and a max-length field is required, not optional.

Google

A third grammar

Doesn't use messages at all — it's contents, with its own names for nearly every setting.

So the one genuinely new thing being built is a translator: a small in-memory adapter that converts a request from the dialect you wrote it in to the dialect of whichever provider actually serves it — and converts the answer back so your code doesn't notice the switch.

The hard part isn't deciding when to fail over. It's that the backup provider speaks a different language — so failover requires translation, and translation has limits.
The key design choice — "fail loud"

The translator deliberately handles only a small, common subset of features that all three providers share. If a request uses something exotic that can't be translated faithfully, the system stops with a clear error instead of quietly sending a degraded request. In ops terms: better to return a clean error than to silently corrupt the payload and hope.

Section 03

The building blocks

Four pieces make up the design. Three of them are concepts you already use in infrastructure — only the translator is new to this domain.

Building block 1

The circuit breaker

Tracks each provider's health and trips "open" after repeated failures so you stop hammering a dead backend. Three states: Closed (healthy), Open (broken, skip it), Half-Open (testing if it recovered). Already exists in the codebase.

You know this asEnvoy outlier detection · Hystrix / resilience4j · the exact thing in your reference image.
Building block 2

The fallback chain

An ordered list of providers to try: primary first, then each backup in turn. Configuration is just "here are my providers, in priority order."

You know this asA HAProxy backend list with backup servers · a priority failover group.
Building block 3

Health-based routing (now) → smarter later

Version one only asks "is this provider up?" But the routing logic is built behind a clean seam so "which is fastest?" or "which is cheapest?" can be added later without rebuilding anything.

You know this asStarting with simple health checks, designed to bolt on least-latency / weighted routing later.
Building block 4 — new

The translator

The one genuinely new part: converts a request into the backup provider's dialect and the response back into yours — for a small common subset only, and failing loud outside it.

Closest analogyA protocol adapter / API normalization layer — but kept deliberately minimal.
Section 04

The circuit breaker, visually

This is the same diagram from your reference image — it's worth understanding because it's the heart of "decides in milliseconds." A circuit breaker is just a tiny state machine that remembers whether a provider is healthy.

Per-provider circuit breaker
Closed → Open → Half-Open → Closed
Closed → OpenThe provider fails a few times in a row. The breaker "opens" and we stop sending it traffic — requests now go straight to the next provider in the chain.
Open → Half-OpenAfter a cool-off period, the breaker sends one test request to see if the provider recovered. (Think: a single canary probe.)
Half-Open → ClosedThe test request succeeds → the provider is healthy again and goes back into normal rotation.
Half-Open → OpenThe test request fails → back to open, keep skipping it, wait and probe again later.
One important detail — it's per-process

This health state lives inside each running copy of your app, not in a shared store like Redis. So if you run 10 replicas, each learns a provider is down on its own. That's a deliberate trade-off (no shared infrastructure to operate), and it's the same way LiteLLM's client-side router and others work. The cost: a freshly started process always pays for the first failure before its breaker opens.

Section 05

What happens on a failure

Here's the path a single request walks. The important idea is the safety gate in the middle — the system only moves to the next provider when it can prove doing so is safe (more on why in the next section).

Request comes in
Check the budget, then ask the router for the providers to try, in order.
try the primary
Primary · OpenAI
Your request passes straight through — no translation on the happy path. If it works, return the answer. Done.
it failed — is failover safe?
The safety gate
Did the request provably never reach the provider (e.g. connection refused, or a "too many requests" rejection)? If yes → safe to fail over. If it's ambiguous (a timeout — it might have run) → stop and surface the error; do not risk doing it twice.
safe → translate & try the next provider
Backup · Anthropic
Now translate the request into Anthropic's dialect (this is the only place translation happens). If a feature can't be translated, stop with a clear error. On success, translate the answer back to your shape and return it.
still failing? continue down the chain…
Settle up
Record which provider actually served the request so billing and dashboards stay accurate, and mark that provider healthy.
Section 06

The four gotchas that keep it safe

This is the part a Platform engineer will appreciate most — it's all operational rigor. Each of these is a way the naive version ("just retry on another provider") quietly breaks in production.

1 · Don't pay (or act) twice

This is the classic at-least-once vs exactly-once problem you know from message queues and retrying POST requests. If a request times out, you don't know whether the provider already did the work. If you blindly retry on another provider, you might get charged twice — and worse, if the request triggered an action (the agent sends an email, files a ticket), that action happens twice.

The rule

Only fail over when the system can prove the request never landed (e.g. the connection was refused before anything was sent). On a timeout — genuinely ambiguous — it does not fail over; it surfaces the original error and lets the caller decide. And note: a retry "idempotency key" can't help here, because a key registered with OpenAI means nothing to Anthropic — they're different companies.

2 · You can't un-send a stream

Many AI responses stream — text arrives token by token, like a chunked HTTP response. Once the first chunk has gone out to the user, you're committed: you can't rewind and switch providers mid-answer.

The rule

For streaming requests, failover is only allowed before the first token is delivered. After that, an error is just an error — same as a load balancer can't re-route a response whose body has already started transmitting.

3 · "Milliseconds" has an asterisk

The marketing line — "switches in milliseconds" — is true, but worth understanding precisely. Once a provider is known to be down (its breaker is Open), rerouting is genuinely instant, because the decision is local state. But noticing the first failure still costs one real timeout.

Exactly like a health-check interval

Your load balancer reroutes instantly once a backend is marked unhealthy — but it took one or more failed health checks to mark it. Same here: the first few requests during a fresh outage absorb the failure; everything after reroutes instantly until the provider recovers.

4 · Timeouts must be bounded

The AI provider SDKs default to waiting up to ten minutes for a response. If you don't cap that, a "hung but connected" provider could make your "instant failover" take half an hour as it crawls down the chain.

The rule

A hard deadline budget wraps the whole chain, and each attempt gets a shrinking slice of it. This is plain timeout tuning — the same discipline as gRPC deadline propagation: the total time is bounded no matter how many providers it tries.

Section 07

What gets built, in what order

The work ships in phases so each one is testable on its own. The first two deliver the core capability; the rest harden it and add the "smarter routing" you can grow into.

Phase 1 · Foundation

Health-based failover between two providers

The routing seam, the ordered chain, the circuit-breaker wiring, and the bounded-deadline safety — for plain text requests, behind a feature flag. Proves "OpenAI down → Anthropic serves" works end to end.

Phase 2 · Translation

The common-subset translator + fail-loud

The request/response converter for the shared feature set, plus clear errors for anything outside it. This is what makes a cross-company hop actually work.

Phase 3 · Hardening

Streaming + the don't-pay-twice rules

First-token-only streaming failover and the full idempotency safety rules from Section 6.

Phase 4 · Accounting

Billing & dashboards stay in sync

The Solwyn Cloud side records which provider actually served each request, so cost tracking and budgets remain accurate after a failover.

Phase 5 · Future

Smarter routing — fastest / cheapest

Drop-in routing policies (least-latency, lowest-cost) that reuse everything above. Designed for now, built later — no refactor required.

Section 08

Why it matters for you

Reliability

Agents survive a vendor's bad day

Provider outages and rate limits stop being incidents. Traffic shifts automatically and recovers automatically — you don't get paged for someone else's downtime.

No new infrastructure

Nothing to deploy or operate

This lives inside the app's library, client-side. There's no proxy or gateway to stand up, scale, secure, or monitor — unlike running your own LiteLLM/Portkey proxy. Zero ops surface added.

Cost stays honest

Billing follows the real provider

When a request fails over, the system reports the provider that actually served it, so dashboards and budget caps don't silently drift.

Trade-offs to know

Keys & feature limits

You must provision API keys for every provider in the chain (a gateway would centralize these — a client library can't). And the most advanced calls may not be failover-able at first, by design.

Section 09

The decisions — now settled

These were the open product calls. They're decided now — captured here in plain terms (the technical spec records the implementation detail).

Decision A · settled

Streaming is in from day one

No shipping without it — streaming failover is too high-value to defer. The one tricky provider (Google streams lazily) gets special handling so it fails over like the others.

Decision B · settled

Tool calls fail over — within a clear line

The stable, shared "call a function" feature is supported. The genuinely risky cases (a tool call caught mid-flight, or vendor-proprietary tools) fail loud instead. Automated round-trip tests are the alarm if a provider ever changes the basics — so it's not endless patching.

Decision C · settled

Safe by default, aggressive by choice

Never double-charge is the default and the floor. Customers who want snappier failover can opt in and tune their own failover timeout — the SDK won't take that risk for them.

Decision D · settled

Provider keys are not our business

A core tenet: Solwyn never accepts, stores, or logs a provider API key (or any prompt). Keys live in your provider clients; we just document that each provider in the chain must be configured.

Decision E · settled

Preset per-provider defaults (e.g. max_tokens)

Because Anthropic requires max_tokens, you can preset it (globally or per provider) at setup. Defaults only fill in a value you left blank — they never override something you set.

Decision F · settled

Pin minimum provider-SDK versions

We'll declare version floors for each provider library (as install extras) so behavior is predictable — while still letting you bring your own client. A belt-and-suspenders error check stays as the runtime safety net.

Section 10

How failover behaves — quick FAQ

The questions that come up first, answered plainly.

Question

If it swaps providers mid-conversation, does my agent lose its memory?

No. AI calls are stateless — your app re-sends the entire conversation on every request, so the backup provider receives the full history and continues seamlessly. Caveat: features that keep state on the provider's own servers (OpenAI's Responses / Assistants) don't transfer — and those aren't failed over at all, so nothing is silently lost.

Question

What does Solwyn actually wrap?

Only the chat / message / generate completion calls. Embeddings, files, images, audio, model listing — everything else passes straight through, untouched. And on the healthy path your request is zero-touch, so the SDK can never block a call your provider would have served.

Question

Can I make Anthropic primary and OpenAI the backup?

Yes — it's fully symmetric; any provider can be primary or backup. (Bonus: Anthropic-first actually avoids the max_tokens gotcha, because Anthropic already forces you to set it.)

Question

What if the backup can't handle my exact request?

It fails loud — a clear error rather than silently sending something subtly wrong — and only ever on the failover path, after the primary already failed. Your healthy calls are never second-guessed.

Section 11

Glossary

The handful of terms worth pinning down, in one place.

TermIn plain language
ProviderAn AI company whose API you call: OpenAI, Anthropic, or Google. The "backend" in this design.
FailoverAutomatically switching to a healthy backup when the primary fails. The whole point of this feature.
Circuit breakerA small state machine (Closed / Open / Half-Open) that tracks a provider's health and stops sending traffic to one that's failing.
Fallback chainThe ordered list of providers to try: primary, then backups in priority order.
TranslationReshaping a request (and its response) between providers' different API "dialects." The new, hard part — kept to a minimal common subset.
Fail loudThe rule that the system raises a clear error rather than silently sending a degraded request when a feature can't be translated.
IdempotencyThe property that doing something twice is safe. Failover has to respect when an operation is not idempotent (e.g. a paid call that may have already run) and refuse to risk a duplicate.
StreamingA response delivered token-by-token (like chunked transfer). Can't be re-routed once it has started.
Rate limit (429)"Too many requests" — the provider throttling you. A common failover trigger, and a safe one (the request was rejected before doing work).
Client-side SDKLogic that lives inside your app's library, not in a separate server. Means no extra infrastructure — but health state isn't shared across replicas.

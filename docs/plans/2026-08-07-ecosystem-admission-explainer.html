Getting Solwyn through the door

Solwyn watches AI spending and stops runaway bills. But the tools most buyers use every day, called agent frameworks, turn Solwyn away at the door. This plan fixes the door check once, then puts Solwyn inside the three biggest frameworks.

01

The problem: a bouncer at the door

Solwyn works like a smart sleeve around a company's AI account. Every request passes through the sleeve, gets a budget check, and gets counted. The sleeve never reads the messages inside.

Agent frameworks are toolkits that teams use to build AI helpers. They are where the customers with runaway AI bills already are. Many frameworks let you hand them your own AI account to use. But before accepting it, they check its ID: "Are you a real OpenAI account?"

Solwyn's sleeve fails that ID check. It acts exactly like the real thing, but its ID says "Solwyn," so the door closes.

Our closest competitor, AgentBudget, wins deals today for one reason: it already works inside these frameworks. We checked our code. We ship zero framework support, while all the plumbing needed for it sits finished and waiting.

Fix the ID check once, and every framework that asks "who are you?" opens up at the same time.

02

The fix: answer with the ID of the card inside

The chosen design is called a transparent proxy (a see-through stand-in). Three small changes make the sleeve invisible to ID checks.

Change one

Borrowed ID

When anything asks the sleeve "what are you?", it now answers with the identity of the real account inside it. This is a proven trick. Big monitoring companies have used it safely for years.

Change two

Name tags on our stuff

Everything Solwyn stores inside the sleeve gets a solwyn_ name tag. That way our stuff can never be confused with the account's own stuff. We found one real clash already (more in section 4).

Change three

Changes pass through

If a framework adjusts a setting on the sleeve, like a timeout, the change now lands on the real account inside. Before, it would quietly land on the sleeve and do nothing.

Here is the life of one AI call once a framework has admitted the sleeve:

Step 1 Your AI helper acts The framework sends a request to what it believes is a normal AI account.
Step 2 Budget check Solwyn asks its cloud: is there money left for this? If not, the call stops here.
Step 3 The AI answers The request goes straight to the real AI provider. Solwyn never touches the words.
Step 4 The receipt Solwyn sends usage numbers to its cloud. Counts and labels only, never message text.
The money safety machinery does not change in this project. Only the front door does.
03

Two ways in, one winner

There were two candidate designs. The plan weighs both and picks the safer one.

Chosen · The mirrored badge

Show the inner card's ID

The sleeve keeps being a sleeve. It just answers ID questions with the real account's identity. Anything the sleeve does not handle itself gets passed to the real account, which does the work with its own tools and its own memory.

Why it wins: there is always exactly one place where the account's real state lives. Nothing can drift out of sync.

Rejected · The costume

Sew the account's own class onto ours

Python allows building a new type on the fly that is legally "both" a Solwyn sleeve and an OpenAI account. Sounds elegant. In practice the account's inner machinery would run against the sleeve's body: it would read from the real account but write to the sleeve.

Why it loses: two memories that quietly drift apart, and every provider update can reshuffle the seams. A slow leak, not a loud crash.

What the mirror trick cannot do

A rare, stricter kind of check asks "is your exact birth certificate OpenAI?" instead of "are you an OpenAI?" The mirror fails that one. We searched: none of the target frameworks check that way. If one ever appears, the plan keeps the costume approach on the shelf as a documented backup.

04

Two surprises found while checking the code

Every claim in the project brief was re-checked against the actual code. Two new facts came out of that sweep, and both changed the plan.

Surprise one

An unwatched side door

OpenAI has a newer calling channel called the Responses API. Solwyn does not watch it yet. Calls through it are not counted and not budget-checked, and today they pass in complete silence.

That matters a lot: OpenAI's own agent framework uses this channel by default. The plan closes the gap two ways: Solwyn will shout a warning if the side door is used, and the setup recipe pins the framework to the watched channel.

Surprise two

A name clash waiting to bite

The sleeve stores the real account under an internal name that OpenAI's own code also uses for something different. Once frameworks accept the sleeve as real, outside code reaching for that name would grab the wrong thing.

That is why build step 1 renames all of Solwyn's internal storage with the solwyn_ tag before the identity fix turns on.

05

Where it ships, in order

Three frameworks, ordered by how much value each unlocks versus how much work it needs. In all three, Solwyn's add-ons only label spending. They never read messages, and the sleeve stays the only thing that counts money, so nothing gets counted twice.

1

OpenAI Agents SDK Full budget control

OpenAI's own toolkit for building AI agents. It has a slot for handing over your account, and it ships no budget feature at all. A vacuum we fill. This one needs no new code from us, just a well-tested setup guide: hand it the Solwyn sleeve, pin the watched channel, and each agent's spending shows up under its own name.

2

LangChain / LangGraph Full budget control

The most widely used framework. It also takes your own account (budget control comes free once the door opens), and it lets outside tools listen to progress events. We ship a small listener that labels spending by chain and by graph step, so the bill reads like a story instead of one big number. This is where the competitor lives; this closes the gap.

3

CrewAI Labels first

A popular framework for teams of AI agents. It does not accept an outside account today, so Solwyn cannot block its calls yet. Honest version one: a listener that labels spending by crew and by task, plus a documented recipe for full control for teams that want to wire it. If CrewAI adds account hand-over later, we are ready the same day.

06

The build plan: eight small steps

Each step is one reviewable chunk with its own tests, written test-first. Nothing ships without the full quality gate passing.

1

Put name tags on everything

Rename all of Solwyn's internal storage with the solwyn_ tag so nothing can clash with a real account's own names.

An automatic check fails the build if any future code forgets the tag.
2

Turn on the borrowed ID

The identity fix itself, plus safe answers for edge cases: copying the sleeve, saving it to disk, listing what it can do.

A test pretends to be a strict framework and confirms the sleeve gets in.
3

Make the side doors loud

The unwatched Responses channel and two "hand me a plain account" shortcuts now shout a clear warning the first time they are used.

Tests confirm the warning fires once and says exactly what to do instead.
4

Add a start/finish switch for labels

Frameworks tell us "a task started" and "a task ended" as two separate moments. Solwyn's labeling tool only worked as one wrapped block. This adds the two-moment version.

Tests cover nesting, wrong ordering, and async use.
5

OpenAI Agents SDK recipe

The setup guide plus a live test that proves admission works, budgets fire on every call, and each agent's spending carries its name.

A scheduled test job re-checks against the newest framework version weekly.
6

LangChain add-on

The spending-label listener, shipped as an optional install so core Solwyn stays lean. Includes the strongest safety test: proof that every framework call really hits the budget check.

The privacy firewall test now also covers add-on code.
7

CrewAI add-on

The crew and task labeler, plus the documented full-control recipe. Honest about what it does and does not enforce yet.

A test pins today's limits, so any CrewAI change that unlocks more flips it loudly.
8

Tell the story

A one-page framework matrix, an updated readme, and the changelog. What works where, in plain terms.

Docs reviewed against the shipped behavior, not the planned behavior.
07

Safety rails that do not move

Three promises hold through every step of this project, and each one is enforced by automatic tests, not by good intentions.

Privacy

No message text, ever

Framework add-ons receive progress events that can contain message text. Our add-ons are built so they cannot even look at those parts, and an automatic scan of the code fails the build if anyone tries.

Accuracy

Every dollar counted once

Only the sleeve reports spending. Add-ons attach labels and nothing else. There is no second reporter, so double counting is impossible by design.

Honesty

Nothing silently untracked

Any path that skips the budget check now announces itself with a clear warning and tells you the fix. Silence was the old behavior. It ends with step 3.

08

What could go wrong, and the answer for each

What could go wrongHow the plan handles it
Frameworks change fast and break our add-ons Add-ons are thin, disposable layers over our own stable event system. A weekly automatic test against the newest framework versions catches breakage without blocking our releases. For the fastest-moving framework we ship only a guide, no code.
A framework uses one of the side doors and spending goes uncounted Loud warnings on every side door, plus a tripwire test that proves each framework call hits the budget check. If a real framework does use one, a pre-designed fix is ready to build.
The borrowed ID confuses a developer while debugging The sleeve's printed description always shows both identities. The docs explain the one question that still reveals the sleeve, on purpose.
Message text leaks through a framework add-on The add-ons subscribe only to events without content. The automatic code scan blocks any attempt to read, store, or log the content-bearing parts.
A framework saves the sleeve to disk or sends it to another process That fails with a clear, helpful error instead of corrupted data. The real accounts cannot be saved that way either, so this matches what frameworks already expect.
Someone wraps a sleeve inside another sleeve Rejected immediately with a plain error message. No double counting, no confusion.
09

The two decisions that need you

Everything else in the plan is settled with evidence. These two are judgment calls where I picked a side and want your sign-off.

Decision one

When a framework copies the sleeve, hand back the same sleeve

Some frameworks routinely make copies of their whole setup, including the AI account you gave them. Question: what should copying the sleeve produce?

If a copy became a second, independent sleeve, the budget would split in two and money could be counted twice. If copying just failed, those frameworks would be locked out again, which defeats the whole project.

a "copy" is the same one sleeve, shared. One budget, one counter, no surprises. The fail-loud alternative is preserved in history if you disagree.

Decision two

Side doors warn loudly in version one; they are not rebuilt yet

The unwatched Responses channel and the two "plain account" shortcuts could each be fully brought under budget control now. That is real engineering work, and we have no evidence yet that the target frameworks use them.

Version one makes every side door loud and adds a tripwire test that tells us immediately if a real framework walks through one. The full fix is already designed on paper, so if the tripwire fires, it becomes a normal, bounded task instead of an emergency.

warn loudly now, build the full fix only on evidence. Say the word if you want it built up front instead.

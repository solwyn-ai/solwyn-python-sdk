01

The problem: budgets are all-or-nothing

A quick refresher on what Solwyn does: it sits inside a customer's app, watches every AI call, and checks it against a spending cap. The cap works. The problem is what happens on the way to the cap: nothing.

Today
After this project
  • At 79% of the budget: business as usual, full price.
  • At 99% of the budget: still business as usual, full price.
  • At 100%: a hard stop. Work dies mid-task.
  • An AI agent job that costs 5 to 30 times a normal chat can slam into the wall halfway through and lose everything.
  • At 80%: the system starts preferring cheaper options for backup calls.
  • At 95%: it can switch the main work to the cheapest model you approved.
  • At 100%: the hard stop still applies. That never changes.
  • The job finishes. It just finishes cheaper.

Between “spend freely” and “hard stop” is where real teams live.

02

The big idea: borrow from the power grid

Power companies solved this exact problem decades ago. On a hot day, the grid does not cut your electricity. It sends a signal, and your smart thermostat eases the air conditioning within limits you set. You stay comfortable. The grid stays up. Same shape here:

The power grid
Solwyn
The utility watches total demand and broadcasts a “pressure” signal.
The Solwyn server watches your spending and sends a pressure level with answers it already sends. No extra traffic.
Your thermostat responds, but only within the comfort range you chose.
The library in your app responds, but only using the backup models you already listed as acceptable.
The thermostat never decides electricity prices.
The app never does price math. The server owns all pricing. The app just follows the server's cheap-to-pricey ranking.
You can see on your bill when demand response kicked in.
Every cost-saving switch is stamped on the record of that call. The dashboard can always show you what happened and why.

04

Three rules that never bend

These are the guardrails the whole design hangs on.

The app never does price math

Only the server knows what models cost. The app just receives a ranking (“this one is cheaper than that one”) and sorts by it. There is no price list hiding in anyone's app, so pricing updates never require an app update.

Only models you approved

The system can only ever pick from the backup list the customer wrote down themselves. It never invents a substitute. If you listed no cheaper option, nothing changes; the dashboard just notes that pressure was signaled and there was nothing to shed to.

Nothing happens silently

Every call made under pressure carries the pressure label. Every call that got switched to a cheaper model carries a “downgraded” label. A cheaper answer that a customer can't explain would destroy trust; a labeled one builds it.

05

First, fix the mixed-up charts

One repair has to come before any of this. Smart routing is only safe if the system's health records are accurate, and today they have a known flaw.

Solwyn keeps a health chart for each AI service: is it up, is it slow, is it failing? Routing decisions read these charts. The flaw: two different services that happen to carry the same label (say, two separate Azure accounts) currently share one chart. Like two patients with the same name sharing one medical file.

Today's flaw
The fix
  • Service A goes down, and service B gets blamed too. Both get avoided.
  • Reports mislabel a switch between them as a “model swap” instead of a real failover.
  • Settings meant for one service leak to the other and can cause errors.
  • Each real service gets its own chart automatically, told apart by its actual web address.
  • No setup work for customers. The common case (one service, two models) still correctly shares a chart.
  • Reports and settings follow the real service, not the shared label.
Why this is step one
Pressure routing means making more routing decisions, more often. Making more decisions from mixed-up charts would just spread the mistake faster. Accurate identity first, clever routing second.
06

The feature that's been asleep

Solwyn already ships a setting called “cost-first routing”: always prefer the cheapest healthy option. Customers can select it today. But it does nothing, because it waits for the server's price ranking, and the server has never sent one. A choice that quietly does nothing is a credibility problem.

Here's the good news this plan confirmed: the wiring is already done on the app side. The light switch is installed, the wires run to the right place, and the moment the server starts sending rankings, every installed app lights up on its own. No customer updates anything. That is also the proof the whole design leans on: the server can improve the system for everyone, everywhere, in one move.

One safety catch before flipping the switch
Not every request can be translated for every backup model (different AI services speak different “languages”). Cost-first sorting must never promote a backup that can't actually handle the request, or saving money would break a working call. The plan adds that check before the server ever sends its first ranking.
07

Your customers' controls

One setting with three levels, plus a per-call override. The backup list itself is always the outer boundary; these settings only decide how much of it pressure may use.

Setting What it allows Status
off Pressure changes nothing. Calls still get the pressure label so the dashboard stays honest. For teams that want visibility only. Opt out
reorder In save mode and deep save: backups re-sort cheapest-first. The customer's first-choice model stays in charge. Mild. Only affects which backup steps in when one is needed. Proposed default
prefer_cheaper Everything above, plus: in deep save, the cheapest approved model takes over the main work. The full “finish the run cheaper” behavior. Opt in
per-call switch A developer can mark any single call “never downgrade this one” (or the reverse), no matter the app-wide setting. For the quality-critical call inside an otherwise flexible app. Always available

How it rolls out without breaking anything

Both sides are strict about unexpected data, so the rollout is a handshake: each side only starts speaking after the other side has learned to listen. An automatic test suite enforces the order; it fails loudly if anyone skips a step.

09

The two decisions on your desk

Everything else in the plan is settled. These two need you.

1. How bold is the default?

When a customer turns nothing on and nothing off, what should pressure be allowed to do?

Recommended Default to “reorder” Backups get cheaper under pressure, but the customer's chosen model keeps the main job. Swapping their first choice is a quality call only they should make.
Default to “prefer_cheaper” The stronger out-of-the-box story: runs finish cheaper with no setup at all. The cost: their primary model can be swapped without them ever choosing that, loudly labeled or not.

2. The shape of the price ranking

This one is technical but sticky: it lands in the server and the future TypeScript version too, so it is expensive to change later.

Recommended Rank each entry in the backup list One ranking number per list entry. Can tell apart two services with the same label, and can rank two models on the same service. Both are needed for deep save.
Keep the old per-provider shape One number per provider label. Simpler, but blind to exactly the two cases above. It was never actually used, so replacing it costs nothing today.
10

What could go wrong, in plain words

The worryHow the plan handles it
Spending hovers right at 80% and routing flip-flops. The server uses entry and exit buffers (in at 80, out at 75), so zones change calmly, not constantly.
Customers feel quality drop and don't know why. Primary-model swaps are opt-in, every switch is labeled, and one line of code exempts any critical call.
Chasing a cheap model breaks a request it can't handle. The translation safety check ships before the server ever sends a ranking. When unsure, it leaves things alone.
The two sides update out of step and reject each other's data. The handshake order is enforced by an automatic test that fails until each step is properly closed out.
A bug in the new signal silently ships broken. If the signal fails to attach, the call proceeds normally (safe), and a counter ticks up on an ops chart so the bug is seen the day it happens.
Another in-flight project touches the same server code. The runaway-protection plan and this one agreed on separate field names and a rebase rule. Both plans document the pact.

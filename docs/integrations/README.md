# Framework integrations

Solwyn separates framework attribution from provider enforcement. The shipped
integration modules consume structural lifecycle data only and are
privacy-firewall-enforced; they do not make provider calls, budget checks, or
settlement events. Enforcement comes from an explicitly admitted
`Solwyn(...)` or `AsyncSolwyn(...)` provider-client boundary in the linked
recipe.

| Framework | Enforcement | Attribution | Hierarchy | Admitted and tested calls | Install and dependency posture | Churn posture |
|---|---|---|---|---|---|---|
| [OpenAI Agents SDK](openai-agents.md) | Yes, through the wrapped `AsyncSolwyn` default client on the pinned Chat Completions path. | Workflow tags plus a stable detached `RunHandle`, reactivated by recipe-local `Model` and `ModelProvider` adapters for each active agent. | Agent runs are children of the enclosing workflow; handoff agents are siblings, and repeated tool turns reuse the same agent run. | `Runner.run` and `run_streamed`, including runner retries, handoffs, function-tool turns, streaming cleanup, and budget denial. Native OpenAI/Azure `responses.create`, `.parse`, and new-response `.stream` are metered by Solwyn core, but the Agents recipe and framework smoke deliberately pin Chat Completions; do not infer coverage for other Responses leaves or compatible providers. | No Agents-specific Solwyn extra and no `solwyn.integrations.agents` module. Install `solwyn[openai]` plus `openai-agents`; the adapter classes live in the recipe and smoke tests. | Recipe-only by design. The locked smoke uses `openai-agents==0.20.0`; the weekly/manual smoke re-resolves the current release. |
| [LangChain and LangGraph](langchain.md) | Yes, only through the recipe's wrapped sync/async clients and exact content-blind raw-response leaf shim. | `SolwynRunScopeHandler` maps structural chain, graph-node, and model callback IDs; a one-shot nomination activates the matching identity only for the provider call. | Explicit LangChain `parent_run_id` edges become Solwyn parent IDs. Missing or inconsistent hierarchy and ambiguous nominations fail closed. | Basic non-streaming Chat Completions only: chain `invoke`, chain `ainvoke`, and a two-node LangGraph `invoke`. Streaming, batching/generate, structured output, Responses, response headers, and raw root-client helpers are not admitted. | `solwyn[langchain]` supplies `langchain-core>=0.3`; the recipe also installs `solwyn[openai]`, `langchain-openai`, and `langgraph`. | The content-free handler ships; the version-sensitive raw-response shim stays exact in docs/tests. The locked smoke uses `langchain-core==1.5.5`, `langchain-openai==1.5.1`, and `langgraph==1.2.11`; weekly/manual smoke upgrades them to current. |
| [CrewAI](crewai.md) | Native LiteLLM: none. The narrow enforcement recipe uses a sync custom `BaseLLM` whose plain-text Chat Completions call crosses a wrapped `Solwyn` client. | `SolwynEventListener` observes only structural crew/task lifecycle sources; it never subscribes to model, stream-chunk, or tool events. | Detached crew and task identities preserve parentage across CrewAI's thread-pool callbacks. Each sequential kickoff gets a fresh generation; overlapping reuse with a live prior task is ambiguous and fails closed. | Native LiteLLM with zero Solwyn budget checks; one sync, non-streaming, plain-text custom-`BaseLLM` call; and sequential `Crew` reuse with a late prior terminal callback. Async crews, streaming, tools, structured output, planning, knowledge/embedding calls, and raw clients are not admitted. | `solwyn[crewai]` declares `crewai>=0.157.0`; add `solwyn[openai]` for the enforcement recipe. CrewAI/LiteLLM resolve in their own dependency group because they conflict with the current Agents stack. | The listener supports the current and legacy CrewAI event import paths. The lockfile carries CrewAI `1.15.16`; an isolated weekly/manual lane upgrades CrewAI and LiteLLM to current. |

These are tested recipes, not a general promise that every framework surface
which accepts a provider-looking object is budget-enforced. Keep the wrapped
client, callback/listener, compatibility shim, and call shape together exactly
as shown on the framework page.
